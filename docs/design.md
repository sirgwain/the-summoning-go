# Engine design

Status: draft, 2026-10-30.

A Go engine, over Ebitengine, for real-time, single-character, grid-based fantasy RPGs in the style of
*The Summoning* (1992): an isometric view of a dungeon, palette pixel art, a character panel,
real-time combat and spellcasting, NPC conversation by keyword, and puzzle-heavy levels of
pressure plates, levers, keyholes, teleporters and movable bodies and objects.

The engine is general. *The Summoning* is its first game: a separate import step converts the
original's data (levels, NPCs, objects, text, art, music) into the engine's content format. The
result plays like *The Summoning* without reproducing its code. Its rules start from the original's
as the specification describes them; exact numeric reproduction is not a goal.

The engine is built from its specification in `docs/spec/`, which describes the game in its own
terms and is complete enough to implement from on its own.

## Goals

- **A general engine for this kind of game.** Nothing in the engine is specific to *The Summoning*;
  its content and its rules configuration live in a content pack.
- **Data driven.** Maps, entities, items, spells, dialogue, rules and the numbers behind combat load
  from content. A new game or a mod is content, not engine code.
- **Easy to edit and mod.** Plain JSON and indexed PNGs, stable IDs, override packs, and an editor
  built on the same rule model the engine runs.
- **The Summoning's look and feel.** Palette pixel art with palette effects, the isometric view,
  panel-style UI.
- **Bigger screens.** A wide world view, collapsible panels, a quickbar, UI text at native resolution.
- **A Summoning importer** that brings over the story, levels, NPCs, objects, puzzles, art and music.

## Non-goals

- Fidelity to the original's code, timing, 16-bit arithmetic or random numbers.
- Writing the original's save files. The importer reads them (below); the engine never writes them.
- A scripting language for now. Rules are data; a scripting layer could later add conditions and
  actions to the same registry.
- Shipping the original's data. See [Distribution](#distribution).

## Overview

```
 Summoning files ──► importer ──► content pack ◄── mods, editor
                                       │
                                       ▼
                 commands ──►  ┌──────────────┐ ──► events (sound, message, effect)
                               │  simulation  │ ──► state for render and UI
                               └──────────────┘
                                       │
                         ┌─────────────┴─────────────┐
                         ▼                           ▼
              render (palette shader)        UI, audio, input
```

- **The simulation never knows about the screen.** It takes commands, advances on a fixed timestep
  and emits events. Rendering and UI read its state.
- **Content is the only input.** The engine reads content packs and nothing else. Only the importer
  reads *The Summoning*'s files.
- **The engine defines mechanisms; content defines the game.** The engine knows what a pressure
  plate, a stat, a spell effect or a damage roll is. Content says which plates exist, which stats a
  character has and how much damage a sword does.

## Simulation

### Shape

```go
type World struct { /* plain data; records refer to each other by ID */ }

func New(p *content.Pack, seed uint64) *World
func (w *World) Update(cmds []input.Command) []Event // one fixed step
```

- **Fixed timestep** at 60 Hz. Durations in content are in milliseconds or ticks, never frames of
  the renderer.
- **Seeded RNG** owned by the world. That makes replays, tests and bug reports reproducible. Exact
  reproduction across versions is not promised. Live play takes its seed from the clock, so each
  launch rolls differently; a given `--seed`, a script and a screenshot run use a fixed one (1
  unless given).
- **Plain-data state.** Records refer to each other by ID, so a save is the state encoded, and the
  editor can inspect anything.
- **Events** tell the presentation what to do: play a sound, show a message, start an effect, open a
  conversation, change level, start a scene.
- **Scenes** cover the non-dungeon parts: intro, character creation, story screens, endings. They are
  content (images, text, choices, actions) run by the same engine.

### The world

- A **level** is a grid of cells. A cell has a terrain type: open floor, a solid wall, a diagonal wall
  that fills half the cell, or a special floor (water, pit, slippery, damaging…). It also holds a list
  of objects lying on it.
- **Entities** (the player, NPCs, monsters, projectiles, rolling balls, movable bodies) have a
  position in world units, a facing, a kind and a set of data-driven attributes.
- **Objects** (items) live on cells, in containers or in inventories. Each has a template from
  content, with weight, slots, uses and effects.

### Movement

Movement is free, not cell to cell, as in the original. The grid is the unit of terrain and triggers,
not of position.

- **World units.** A position is in world units, 32 to a cell (the original's world pixels), held as
  integers. An entity moves in eight directions by a step from its kind.
- **Ground point.** An entity's position is the point where it stands on the ground, and its sprite
  has an anchor drawn at that point. The cell under the ground point is the entity's cell: it
  decides terrain effects and fires enter and leave events, so a character can stand partly over a
  neighboring cell without triggering it.
- **Terrain.** A move is tested at the ground point against the terrain. If blocked, the step shrinks a unit
  at a time until it fits, so a character slides up to a wall rather than stopping short.
- **Entities.** Each template has a footprint, a square of world units around its ground point. A
  move that would overlap another entity's footprint backs off.
- **Diagonal walls.** A diagonal wall names the corner of its cell it fills; walking along an axis
  into that corner slides along it.
- **Pushing.** The player pushes pushable things (bodies, boulders, conjured objects) ahead,
  recursively, at an exertion cost.
- Projectiles and rolling things test their corners instead of the ground point.

The step sizes and rectangles are content, per template.
- **Visibility and activity.** What the player can see (line of sight on the grid) and which entities
  are active (a radius around the player) are simulation concepts, independent of how large the view
  on screen is.

### Rules: triggers and puzzles

Puzzles and story logic are rules: an event, conditions and actions.

```json
{ "id": "l3.plate_gate",
  "on": { "weight_changed": { "cell": [12, 7] } },
  "if": [ { "weight_at_least": { "cell": [12, 7], "value": 50 } } ],
  "do": [ { "open": "door.l3.east" }, { "sound": "sfx.gate" } ],
  "else": [ { "close": "door.l3.east" } ] }
```

- The engine has a **registry** of events (enter cell, leave cell, weight changed, object placed,
  item used on, lever pulled, keyword spoken, entity died, timer, level entered…), conditions (has
  item, flag set, counter compare, weight at least, entity alive, stat at least…) and actions (open,
  close, toggle, teleport, spawn, remove, give, take, set flag, add to counter, message, start
  conversation, play sound, start scene, change level…).
- Rule state (flags, counters, timers) is in the world's state, never in the rule.
- The editor builds rules by choosing from the registry. Validation checks every reference.
- Standard puzzle pieces (pressure plate, lever, keyhole, object hole, teleporter, door, magic mouth,
  rolling ball) are content templates built from rules, so a level author places a pressure plate and
  sets a few fields rather than writing rules by hand.
- **First form.** The engine starts with those pieces as typed cell features (door, lever, weight
  plate, item slot, teleporter, exit, trapdoor, gem socket, mouth), each with its own state, and with
  **procedures**: named action lists from the registry that features run when they fire (a lever's
  procedure a and b, a plate's going down and up). The Summoning's level procedures import one to
  one as procedures. General event and condition rules come later, over the same actions.

### Characters, stats and combat

- **Attributes** are declared in content (for the Summoning: strength, dexterity, intelligence and so
  on, hit points, magic points, weapon skills, magic classes). The engine treats them as named
  numbers.
- **Combat is a module.** `engine/combat` defines an interface the simulation calls: attack timing,
  whether an attack hits, damage, armor and resistances, experience on a kill, and the effect of
  exertion and wounds. A rule set implements it, and a content pack names the rule set it uses and
  gives its parameters.
- **The first rule set is the Summoning's** (`engine/combat/summoning`), implementing the formulas
  in `docs/spec/combat.md` with their constants as parameters.
- A game that wants different combat writes another rule set or tunes the parameters.
- **Leveling** and character creation (point allocation, classes, premade characters) are content.

### Spells

- A spell is content: its gesture, cost, requirements (skill class and level), targeting
  (self, direction, cell, entity) and a list of effects drawn from the same action registry as rules,
  plus projectile, area and duration effects.
- Gestures are learned, not just looked up. The player knows a set of gesture icons (from scrolls,
  conversations and the starting school) and enters gestures in the spell-learning UI. A gesture that
  matches any spell, read or not, puts the spell in the player's spellbook. After that the spellbook
  lists it, and memorizing it is one click instead of re-entering the gesture.
- Memorizing and casting keep the game's rules: per-school capacity, random forgetting past it, one
  memorization used per cast, the cost, the conditions and the gesture's cast time
  (`docs/spec/spells.md`).
- The UI sends the commands (`learn gesture`, `memorize spell`, `cast`). Hotkeys and the spell
  panel send the same `cast` command.

### NPCs and dialogue

- Conversation is keyword driven: an NPC has topics keyed by keywords, each with text, conditions and
  actions (give, take, set flag, join, turn hostile). New keywords are learned from text.
- **AI** is a small set of behaviors chosen by content (wander, guard, chase, flee, keep distance and
  cast, follow a path), each with parameters.

## Content pack

```
pack.json                  id, version, dependencies, load order
palettes/                  palettes and remap tables
sprites/<bank>.png         8-bit indexed PNG sheet; <bank>.json frames, anchors, animations
tiles/                     floor and wall sets
fonts/
text/<lang>.json           strings by ID
messages.json              the engine's own messages, by key, pointing at strings
attributes.json            the stat model
items/<id>.json            item templates
things/<id>.json           templates for creatures, boulders, traps and other standing things
portraits/<id>.json        faces, and the figure colors they give the player
looks/<id>.json            how cell features draw in each state
spells/<id>.json
templates/<id>.json        puzzle-piece templates (plate, lever, teleporter…)
levels/<id>/level.json     grid, placements, rules
scenes/<id>.json
flipbooks/<id>.json        animations rendered ahead: view effects, sparkles
audio/music/<id>.wav       or .ogg, with loop points in a sidecar <id>.json
audio/sfx/<id>.wav
audio/cues.json            the sounds of the engine's cues
```

The file formats are in [pack.md](pack.md).

- **The engine's own terms.** The format is designed as if no game existed before it: names, ground
  points, named states and hooks, never an original game's codes or byte layouts. Importers
  translate.
- **Stable string IDs** (`thing.guard`, `item.healing_potion`). Mods override and add by ID.
- **Indexed PNGs** keep palette effects working on edited art. A true-color sprite is allowed and
  simply opts out of palette effects.
- **Levels** are the engine's own JSON, edited with the editor.
- A level's `map` setting is `shown` (the default), or `refused` with either a message ID or a
  conversation ID, which runs when the player tries to open the map.
- `verify` checks a pack: schema, every ID resolves, every rule uses registered events, conditions and
  actions, every sprite frame exists.

## Rendering

- **Palette shader.** Indexed sprites upload as index images (the index in the red channel), the
  world draws in indexes into an offscreen buffer, and a Kage shader looks each index up in the
  current palette, passed as a uniform array (Ebitengine requires a shader's source images to be
  the same size, which rules out a palette texture). Fades, flashes, remapped creature colors and
  color cycling change the lookup, not the art.
- **World buffer.** The world draws into an offscreen image at the art's pixel scale, then scales to
  the window by a whole number. UI draws at native resolution on top.
- **Projection.** Pixel-art isometric (2:1), as the Summoning draws: the grid is turned 45 degrees,
  cells 64 pixels apart along a screen row and 16 pixels between rows, each cell's art in a 32×32
  box, and a world point (x, y) lands on screen at
  ((y − x), (x + y) / 2) from the view's origin. Walls rise from their cell's diamond. The cell size
  is content.
- **Draw order.** Floors first, then walls, objects and entities in one list sorted back to front
  by their depth (x + y of their ground points), each frame.
- **Walls** are one sprite per cell, from a **wall set**: one sprite for each wall shape (straight,
  corner, end, diagonal…), with its face, upper part and edge caps already composed. The importer
  composes the original's pieces into wall sets. A wall whose look changes in play (a door, a secret
  wall) has a sprite per state. The level stores each wall cell's shape, so drawing a wall is a
  straight lookup: wall set + shape (+ state) → sprite.
- **Wall decorations** (torches, banners, carvings) are separate, possibly animated sprites placed on
  a wall face and drawn right after their wall. They are never baked into wall art.
- **View size is free.** A wider window shows more of the level; it does not change the simulation.
- Optional post shaders (CRT, scanlines) are presentation only.

## UI

- **Frames.** The engine draws its own panel frames, in the Summoning's spirit but not its art:
  generated from noise and rules (`engine/frame`) at any size, so no original art is needed. A
  frame is `frame.Width` (8) of the panel's own pixels on each side, scaled with the panel, with
  12 × 12 corner pieces. Its inside is left clear, for each panel to fill as see-through as it
  needs. The layout leaves room for it: a panel's `Frame` is its `Rect` grown by
  the frame, and the panels and the view keep clear of it and take the pointer over it.
  - _Iron and sapphire_ frames the hotbar, the inventory panel and the frontend's menus:
    blue-black brushed iron with a bevel and evenly spaced rivets, a faceted sapphire at each
    corner. A menu's buttons are iron plaques; the chosen one is lit steel with a blue edge,
    and a sapphire at each end where the label leaves room, and the one under the pointer is
    lighter.
  - _Runic slate_ frames the spell panel: dark layered slate cut with small runes and a ring at
    each corner, lit blue. The light breathes, in three groups of runes out of step, a cycle of
    about four seconds.
- **Text** uses the engine's own pixel font (`engine/font`), drawn for the project in the
  spirit of the original's lettering, not copied from it: letters at most 5 pixels wide, capitals
  7 high with 2 below the line, filled light with a dark outline so they read over any art, on a
  fixed advance of 6 and lines 16 apart. It covers printable ASCII; any other letter shows as
  `?`. It is drawn from an atlas at whole scales only, tinted for color, so it stays crisp. A
  larger face of the same letters, a third bigger (at most 7 wide, capitals 9 high with 3 below
  the line, an advance of 8 and lines 20 apart), letters the frontend's menus and screens, which
  are laid out by its measure. A pack supplying its own font is for later.
- **Hotbar.** A bar along the bottom of the play view, always shown: the player's portrait, gauges
  for hit points, magic points and load, the two hands with their action buttons, the twenty
  shelves in two rows of ten, and later the memorized spells. It is how the mouse plays: clicking
  the player takes and puts down, clicking a box swaps it with the object on the pointer
  (`docs/spec/items.md`, The mouse).
- **Inventory panel.** Opened on demand: the figure (a mannequin) with its worn slots, the pack of
  the bag in the left hand, the player's stats and the chosen object's details. It shares the
  hotbar's slot boxes and the code that moves objects between the pointer, slots and floor; the
  hotbar leaves out the mannequin and the stats. The world runs while it is open, as the game's
  does; the spell panel holds it: its commands act, but no time passes (`docs/spec/items.md`,
  Holding the world).
- Collapsible character, inventory and spell panels; the world view takes the freed space.
- Number keys for the hotbar's usable objects.
- Spell gestures with the mouse, plus hotkeys and a spell list.
- **Spellbook.** The spell panel keeps every spell the player has discovered by entering its
  gesture (the player's spellbook, kept in saves), so a spell once found never has to be recalled
  as keys or a gesture again. It shows as a scrollable list, by school, each row the spell's icon,
  name, gesture, cost and how often it is memorized, with a Memorize button that memorizes it once
  more, exactly as entering its gesture would (the school's limit and forgetting apply). Each
  school's heading shows its memorizations of its limit; the list shows eight rows and scrolls
  with the wheel, Page Up and Page Down and its scroll bar.
- Conversations with keyword entry and a list of known keywords.
- **Conversation log.** Every conversation is remembered: whom it was with (the speaker's
  portrait and name), on which level and when in play time, and each line said and question asked
  in order, with `@` and keywords as shown. A window, opened with L and from the hotbar's Log box,
  lists the people talked with by portrait and name; choosing one shows its conversations, newest
  first, and a search field finds text across all of them, jumping to the line. The world waits
  while it is open. The log is world state, kept in saves (`docs/spec/dialogue.md`, Engine
  model); the transcript file stays as the game's printing option.
- **Book.** A record of the creatures and items the player has come across, opened with J and
  from the hotbar's Book box: each by its picture and name, and what the player has learned of it,
  revealed in stages: a creature seen, fought, then killed, its defenses only once met; an item
  seen, handled, then used; a scroll's spell from first sight. A field filters it by name. What it
  says is worked out from the templates, with a pack's optional `lore` and `effect` texts.
  The book is world state, kept in saves (`docs/spec/player.md`, The book).
- **Magnify floor objects**, a game setting: objects lying on the floor draw with their larger
  inventory image instead of their small floor image, so they are easier to see and to click.
  An item template carries both images (`docs/spec/items.md`). Presentation only.
- A level map, always available, with no item needed: a minimap in a corner of the view, and a
  full-screen map on a key. Both show only the cells the player has seen. A level can refuse the
  map (`docs/spec/world.md`): the minimap then hides, and opening the map shows the level's message
  or starts its conversation instead.
- **Map of past levels and their links.** The full map can switch to any level the player has
  visited, showing that level's seen cells (kept per level). It is interactive: hovering a
  teleporter, exit, pit or trapdoor the player has used shows where it took them, a line or a
  label to each destination they have travelled through it (one teleporter can have several);
  hovering a lever, plate or slot whose effect the player has seen shows what it changed (the doors,
  walls and floors that moved when it was used while in sight). Only what the player has
  observed is shown: the world records each use's destination and each switch's seen effects,
  and keeps them in saves. The tools show the same links without the observing (below), and are
  built first.
- Esc closes the topmost window over the view (a conversation, the map, the spell panel, a scroll's
  picture, the inventory), one per press; with none open it opens the options menu, as O does.
- The UI only sends commands; it never changes game state directly.

## Input

`input.Command` names what the player does (walk, pick up, put down, swap a slot, use; attack and
cast later). Keys, mouse and gamepad bind to commands in a user configuration. Replays record
commands. A walk is asked for each update the walk is held, and taken at the player's next update.

**Debug commands** act on the world directly, without a player: use the lever at a cell, drop or
remove an object on a cell, put weight on a plate or take it off without an object, place an
entity on a cell (running the cell's enter and leave effects),
switch a cell's feature on, off or over, reset a feature to how the level starts it (a plate
keeping the weight on it), run a procedure, follow an exit, put the player on a cell.
They go through the same
command path as the player's, so the viewer can test a level's mechanisms before the player exists
and the editor's play-test can use them later. A game build can leave them unbound.

## Audio

- Music and effects play from WAV or Ogg files with loop points.
- The Summoning's music and effects are AdLib (OPL) sequences. The importer renders them once: it
  plays each sequence through an OPL2 emulator (`internal/opl2`, a Go port of opal) and writes WAV
  with loop points. The sequence format and how it plays are in `docs/spec/audio.md`; the work is
  planned in [audio-plan.md](audio-plan.md).
- `engine/audio` decides what plays and `engine/audio/speaker` plays it through Ebitengine, so the
  rules test without a sound card. The simulation names sounds by cue (`lever`, `door`,
  `level_up`, …) and the pack maps cues to sounds.
- **Sounds layer.** The game played one song at a time, so an effect waited for the music to end
  and for any higher-numbered effect, and starting a sound cut off the one before. The engine
  keeps no such limit: music has a channel of its own, one track at a time, and effects sound over
  it and over each other. A cue always plays as an effect, so a fanfare sounds over the music
  instead of stopping it; an effect started again while it sounds restarts rather than doubling.
- The fades lower the music's master volume, 0..127, by 3 a step, applied as up to 47.25 dB of attenuation
  (a carrier at full output level). The quick fade steps every 1/18.2 s as the game does; the slow
  fade, which in the game steps with the song's events, steps every 125 ms, about the mean over the
  game's looping tracks.
- F9 cycles music and effects, effects only, and silence, as the game's music key does; F8 is quick
  load. `--mute` plays nothing.

## Saves

- A save is the world state, versioned and encoded as compressed JSON.
- It records the content packs and versions it was made with, and warns on a mismatch.
- Quick save, quick load and autosave on level change.
- No save is taken while a conversation is open (but for the disk menu), or while a transition,
  a view effect or sparkle plays or something waits for one; the autosave waits until they end.
- `play --load` takes a save file's path, or a name in the saves directory (`--load quick.sav`).
- The Summoning importer converts the original's save files into engine saves (`docs/spec/saves.md`),
  so a game begun in the original carries on in the engine.

## The Summoning importer

`importers/summoning` reads a user's copy of the game's twelve data files and writes a content pack.

- **Formats.** The importer reads the files as `docs/spec/formats.md` describes them.
- **Meanings.** Each spec maps the original's fields to the engine's model; the importer follows
  those mappings.
- **Mapping, not copying.** Original records become engine content: cells and walls to the level grid,
  OBJECTS to item templates, NPC to creature templates, TEXT and KEYWORDS to strings and dialogue,
  INTERACT and the level procedures to rules and puzzle templates, RESOURCE sprite banks to indexed
  PNG sheets, COLORS to palettes.
- **Summoning defaults.** The importer also writes the Summoning's stat model, combat parameters,
  spells and character creation, as the specs give them.
- **Report.** Each import writes a report of anything it could not map, so gaps are visible.
- **Saves.** `import-save` reads the game's save files with its data files and the imported pack, and
  writes engine saves: a new world on the pack with each save's state laid over it.

## Editor

A separate program (`cmd/editor`) for building content packs. It shares the engine's renderer, UI
widgets and mouse handling, so a level looks the same in the editor as in the game, and it reads and
writes the same pack format.

- **Levels.** Paint terrain, place walls, objects, creatures and puzzle templates, and see the level
  in the game's projection with its animations running.
- **Walls.** The author paints wall cells; the editor picks each cell's shape from its neighbors
  (straight, corner, end, diagonal) so ends and corners are always capped, and stores the shape in
  the level. The game never works shapes out at run time.
- **Decorations.** Placed on wall faces and shown animating, so the author sees the level's feel.
  The editor allows a decoration only on a face that borders open floor.
- **Rules.** Build rules from the registry's events, conditions and actions, with references picked
  from the pack.
- **Content.** Edit items, creatures, spells, dialogue and text as forms over the pack's JSON.
- **Links.** Hovering a teleporter, exit, pit or trapdoor shows its destinations, across levels
  too; hovering a lever, plate, slot or trigger shows the features its procedures change. In the
  editor and the viewer's tools these come from the pack (every link, observed or not); the game's
  map shows the same overlay limited to what the player has observed (UI). The viewer gets it
  first, as the tools already list a feature's hooks and procedures.
- **Conversations.** A creature's conversation reaches the level too: what its clauses do,
  directly or through the procedures they `run`, is a link from the creature, dashed (it happens
  only in talk) and labeled with the conditions of the clauses that do it. Selecting a feature
  lists the creatures that act on it; selecting a creature shows its conversation a line per
  clause (the condition, then the actions, numbered as jumps number them), whether the player has
  talked to it, and the counters its clauses test or set with their values.
- **The full book.** The viewer's tools open the player's book (J) with everything exposed: every
  creature template and item of the pack, come across or not, at the last stage and with every
  defense known, then where it is on the current level (a creature's things; an item on the floor,
  in a container, carried, taken by a slot, made or shot by a procedure, given or taken by a
  conversation of a creature there) and its whole record, a line a field: an image (an icon, a
  floor image, a doll) as its picture, an item's actions and power and a creature's behaviors in words, a text key with its words, its animations as
  their frames (of those made for each direction, the down-right one's), at twice their size as
  the book's pane shows its pictures. Clicking where
  it is closes the book and selects it there, the view centered on it. The pane scrolls with the
  wheel. It lists the current level's entries alone until Tab, or its toggle, lists them all;
  the current level's are marked in green either way.
- **Play-test.** Start the simulation from the level being edited.
- It runs `verify` continuously and shows broken references where they are.

## Specification

`docs/spec/` describes the game the engine runs and the files the importer reads. It is the source
of truth: code implements the spec, and a change in behavior starts as a change to the spec.

- **Self-contained.** An implementer with only the spec and a copy of the game's data files can build
  the engine and the importer. The spec cites no other implementation.
- **In its own words.** Behavior is described as rules, tables and math, not as code.
- **Each topic** gives the engine's model (which becomes the content schema), how the original's

## Testing

Everything the game does is testable without a display and without the original's data.
Tests can also check the engine against the game's own files, when given them, and skip without:

- `SUMMONING_DATA` names the directory of the game's data files; those tests import a pack from it.
- `SUMMONING_SAVES` lists directories of the game's saves (separated as `PATH` is), one per case,
  as `<case>/SAVES/dNNN.sav` or `<case>.sav`. A case's save is made just before something happens
  (a view effect, a fall, a teleport); the test does what makes it happen in the engine and checks
  the outcome (`importers/summoning/gamedata_test.go`). A case without its save is skipped.

- **Simulation.** Tests build small packs in code, send commands and check events and state.
- **Input snapshots.** The presentation reads its input once per update into plain data: keys
  held, pressed and released, the cursor, the mouse buttons and the wheel. The code that turns a
  snapshot into commands and view changes (the viewer's controls now, the game's later) does not
  import Ebitengine, so tests feed it snapshots as a player would.
- **Scripts.** A script is JSON: input by update number (keys, clicks on cells, selections), and
  when to take a screenshot or dump the state. The viewer runs a script in its window, with the real
  renderer, ignoring live input, and exits when it ends. Tests run the same scripts without a
  window, skipping screenshots.

  ```json
  [ { "at": 0,  "select": [12, 7] },
    { "at": 1,  "keys": ["U"] },
    { "at": 90, "shot": "lever.png", "dump": "lever.json" } ]
  ```
- **State dumps.** The world's state as JSON in the pack's terms (features with their fields as
  they are now, things, objects on floors, changed cells), with the viewer's selection and event
  log. Tests and tools check state from a dump rather than from pixels.
- **Dev pack.** A pack generated by code (`devpack`): a palette, plain drawn art for floors, walls,
  doors, levers, plates and the other features, a few items and things, flipbooks for the view
  effects and sparkles, and levels that lay out each mechanism. It is made by code, so it can live in the repository: tests build it in memory,
  and `summoning devpack` writes it to `packs/dev`, which is checked in so the viewer can open it
  without generating it. A test fails when the checked-in copy is out of date with the code.
- **Dev pack in the game's art.** `devpack.Dress` dresses the dev pack in another pack's art: the
  same levels, records and ids, drawn with that pack's palette, tiles, feature looks, figures,
  icons and flipbooks. Walls are shaped by their neighbors and the floor under them halved as the
  game does. `devpack.GameArt` names the records of a pack imported from the game, so
  `summoning devpack --art packs/summoning` writes `packs/dev.game`, which stays local. With
  `SUMMONING_DATA` set, the dev pack's play tests run a second time on the dressed pack.

## Distribution

The original's data is copyrighted and is not in this repository. The importer reads the user's own
copy and writes the pack locally; that pack is not committed or distributed. The engine, the importer
and original content made for the engine can be distributed. Tests use small hand-made fixtures, not
original data.

## Milestones

Progress, and the work each milestone has left or handed on, is in [design-notes.md](design-notes.md).

1. **Viewer.** Import levels, sprites and palettes; draw a level with the palette shader in the
   isometric projection; move a camera.
2. **World.** The level's mechanisms, without a player. Import cell features, procedures, item and
   creature templates, and what each level places (creatures and their inventories, boulders,
   traps, exit markers, mouths, objects on floors and in containers). The simulation holds every
   level's state and runs doors, levers, plates, item slots, teleporters, trapdoors, pits, the gem
   socket and deep water. The viewer draws the simulation's state, selects a cell or an entity with
   the mouse and shows its stats and state, and triggers mechanisms by debug commands.
3. **Harness.** What [Testing](#testing) describes: input read as a snapshot per update, the
   viewer's controls without Ebitengine, scripts, state dumps, and the dev pack.
4. **Walk.** Player entity, movement and collision, pushing, visibility, rolling boulders; pick up,
   drop and use; the hotbar, with the mouse taking objects, moving them between the pointer and
   the shelves and hands, and putting them down (a key into a keyhole); the portraits, which give
   the player's figure its colors; a level whose puzzles can be solved by playing it.
5. **Fight.** Attributes, combat pipeline, creature AI and animation, projectiles and arrow traps.
6. **Inventory.** The inventory panel over the hotbar's slot code: the mannequin with the worn
   slots, the pack, the stats, an object's details; the game's object icons, without its panel art.
7. **Magic and talk.** Spells and gestures, dialogue and keywords; spells on the hotbar.
8. **Game.** Scenes, character creation, saves, audio; *The Summoning* playable from start to end.
9. **Remaster UI.** Wide view, panels from the game's art, hotkeys.
10. **Modding.** Override packs and `verify`, then the editor.

## Decisions

- **Movement:** free movement in world units, as the original; the grid holds terrain and triggers.
- **Combat:** a module behind an interface; the first rule set is the original's formulas.
- **Editor:** a separate program sharing the engine's rendering, UI and mouse handling.
- **Fonts:** a custom outline font drawn for the project, at native resolution.
- **Projection:** 2:1 pixel-art isometric, as the original.
- **Walls:** composed into one sprite per wall shape on import; the editor chooses shapes, the
  renderer only looks them up. Decorations stay separate, animated sprites.
- **Wall caps:** each wall draws only its own caps. The engine redraws the whole view back to front
  each frame, so a wall in front always covers the one behind it.
- **Spells:** learned once by entering the gesture, then memorized from a spellbook. The
  memorization and casting rules stay the game's.
- **Map:** built into the UI rather than tied to the Palimpsest. Levels can refuse it with a
  message or a conversation.
- **World before player:** the level's mechanisms are built and tested through debug commands
  before the player, movement and combat exist.
- **Rules first as features and procedures:** typed puzzle pieces running action lists; general
  rules come later over the same actions.
